# ADR-0002 真实日历/邮件服务接入评估

> 状态：accepted（2026-08-21） · 权威需求：`一人公司AI-Agent需求文档_v2.5.md`
> 关联：`src/skills/calendar-skill/`（E162/E166）、`src/reminder/reminder-store.ts`（E163/E165）、
> `office-daily` email 模式（E162）、[ADR-0001](./0001-architecture-foundation.md)

## 背景

日历与提醒目前全部为本地 SQLite（`calendar_events` + `reminders`），邮件只有草稿生成
（会议邀请 md / 回复草稿），未接任何真实服务。本 ADR 评估“接入真实日历/邮件服务”的
可选路线并定下决策，为后续实施提供方向；本轮不产生代码改动。

约束（来自 ADR-0001 / 需求宪法）：

- 本地优先桌面应用，离线可用优先，无 Docker。
- 外部服务全部经过适配层，不散落在核心域。
- 运行时数据（含凭据）进 `data/`，git 忽略、不提交。
- 行为或参数变更仍需走“计划 → E-NN → bench”纪律。

## 决策

### 1. 日历：本地优先 + 阶段式接入

| 阶段 | 内容 | 结论 |
|------|------|------|
| 现状 | 本地 SQLite 日程 + 重复日程（E162/E166）+ 重复提醒（E163/E165） | 保留为唯一权威数据源 |
| 阶段 1 | 本地 `.ics` 导出/导入（iCalendar） | **采用**：离线可用、无 OAuth、可导入 Outlook/Google/Thunderbird/QQ 邮箱 |
| 阶段 2 | CalDAV 双向同步 | 采用（可选）：仅当用户已有 CalDAV 服务（Nextcloud/Radicale/iCloud 等）时按适配层接入 |
| 阶段 3 | 云 API 双向同步（Google Calendar / Microsoft Graph） | 暂缓：需要 OAuth 桌面流与云依赖，仅当用户明确要求与真实云日历双向同步时再做 |

### 2. 邮件：草稿 → SMTP 发送（用户确认制）

| 能力 | 内容 | 结论 |
|------|------|------|
| 草稿生成 | 会议邀请/回复草稿（E162 现有） | 保留，发送前必须预览确认 |
| 发送 | SMTP + TLS（Gmail/QQ/163/Outlook 等应用专用密码） | **采用（阶段 1）**：发信是显式用户动作，凭据本地存储 |
| 收信 | IMAP 拉取/本地归档 | 暂缓：收益低、维护面大，后续按需评估 |

### 3. 安全与边界

- 凭据仅存 `data/`（git 忽略），候选 Windows DPAPI 加密；不写进需求文档与日志。
- 日历/邮件接入全部走适配层（`src/` 新增 adapter），核心域不直接依赖外部 SDK。
- 任何真实发送/同步都是显式用户操作：先草稿预览 → 确认后才执行。
- 不把本地记忆、文件、搜索历史上传到任何日历/邮件服务。

## 备选方案

| 方案 | 结论 | 原因 |
|------|------|------|
| 只做云 API（Google/Graph）一步到位 | 暂缓 | OAuth 桌面流复杂度高、离线不可用、与本地优先冲突 |
| 邮件用 Outlook COM / MAPI 直连 | 否决 | 依赖本机 Office 环境、脆弱难测，违背“外部服务经适配层” |
| 日历继续纯本地、不做任何互操作 | 保留为兜底 | 已满足核心需求；互操作为增量价值 |
| 自建日历服务器（如 Radicale 本地部署） | 可选 | 阶段 2 时可作为 CalDAV 服务端选项，非默认 |

## 后果

正面：

- 阶段 1（.ics + SMTP）零 OAuth、离线可用、无新重型依赖，符合“核心依赖精简”。
- 方向明确后，后续实施可复用现有 `calendar-skill`/`ReminderStore`/draft 生成链路。
- 凭据与发送动作的安全边界提前定死，避免“后台静默发信/上传”。

代价：

- 阶段 3（云双向同步）若最终需要，仍需补 OAuth 桌面流与刷新令牌管理。
- `.ics` 导入导出是文件级互操作，不是实时推送，用户需要手动导入/导出。

## 状态

accepted（方向决策已定，实施分阶段排期；无代码行为变更，不登记 E-NN）。
